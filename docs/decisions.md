# Decisions

| Date | Decision | Where |
| ---- | -------- | ----- |
| 2026-09-14 | One application chart, with aliased sub-charts for the stores (`deploy: true/false`), a `values.lint.yaml`, helm-unittest suites, examples, and CI for lint, tests and OCI release | `charts/rikoo`, `.github/workflows` |
| 2026-09-14 | Sub-charts picked to keep the images the product already runs: `groundhog2k/postgres` with a pgvector image, `groundhog2k/redis`, `minio/minio` standalone. No Bitnami chart, for licensing reasons | `Chart.yaml`, `values.yaml` |
| 2026-09-14 | **`rikoo.image.registry` and `rikoo.image.tag` are required**, with no default and no fallback on `appVersion`: an image without a version is a mistake, and the registry depends on the release pipeline | `_helpers.tpl`, `validations.yaml` |
| 2026-09-14 | The **sealing pair is never generated by the chart**: Helm cannot derive a public key from a private one, and a regenerated pair would make every sealed secret unreadable. It comes from OpenSSL, and the private half is mounted as a **file** in the worker alone, which is the recommended production path | `templates/secrets/sealing-secret.yaml`, `rikoo.sealing.volume` |
| 2026-09-14 | Symmetric keys (widget signing, visitor identity, TOTP, sandbox token) are generated on first install and kept (`lookup` plus `resource-policy: keep`), pinnable with `value` or `secretKeyRef`, in one Secret named `<release>-app` | `templates/secrets/app-secret.yaml` |
| 2026-09-14 | `DATABASE_URL` is assembled with `$(RIKOO_DB_PASSWORD)`, expanded by Kubernetes: no literal password in a manifest. A managed database supplies a complete URL from a Secret instead | `_helpers.tpl` (`rikoo.databaseEnv`) |
| 2026-09-14 | Bundled PostgreSQL: the application role **is** the superuser of that instance, because the first migration creates the pgvector and citext extensions. A managed database brings its own role | `templates/secrets/postgresql-secret.yaml` |
| 2026-09-14 | Migrations run as a Helm `post-install` and `pre-upgrade` Job from the api image, **and** the api entrypoint replays the same idempotent, advisory-locked command. `pre-install` is impossible with a bundled database: the release has not created it yet | `templates/migrations/job.yaml` |
| 2026-09-14 | The worker waits for a healthy api through a `wait-for-api` init container on `/readyz`, which can be switched off | `templates/worker/deployment.yaml` |
| 2026-09-14 | The sandbox's isolated network becomes three **NetworkPolicies**: core to Playwright only, Playwright to the egress proxy only, and the proxy reachable from Playwright only. The api matches no ingress rule, so the boundary is topological. Requires a CNI that enforces them | `templates/mcp-sandbox/networkpolicy.yaml` |
| 2026-09-14 | The sandbox core runs as uid 0 with exactly `SETUID`, `SETGID`, `CHOWN` and `DAC_OVERRIDE`, on a read-only root filesystem and without privilege escalation: that is what gives each run a distinct unprivileged identity. Pod Security Standard *baseline* for that pod, *restricted* for every other | `templates/mcp-sandbox/core-deployment.yaml` |
| 2026-09-14 | Sandbox workspaces use an `emptyDir` by default, an ephemeral scratch buffer per run and never a source of truth; a PVC is opt-in. One replica, `Recreate` strategy | `values.yaml` (`rikoo.sandbox.core.workspace`) |
| 2026-09-14 | One `ServiceAccount`, with no `Role` and no mounted token: no Rikoo process talks to the Kubernetes API. The account exists so cloud identities can be attached through annotations | `templates/serviceaccount.yaml` |
| 2026-09-14 | Non-secret configuration lives in **one** ConfigMap consumed through `envFrom` by both api and worker, with a checksum computed from the values so a configuration change rolls the pods. What is computed, secret or service-specific stays in `env` | `templates/configmap-env.yaml`, `rikoo.configChecksum` |
| 2026-09-14 | Per-service OTEL routing is modelled by `rikoo.otel.api.*`, and conversational content capture is **off** by default | `values.yaml` (`rikoo.otel`) |
| 2026-09-14 | Refusal tests (`fail`) live in a dedicated suite over `validations.yaml`: helm-unittest renders only the templates a suite lists, and `required` is neutralised in lint mode, hence an explicit `fail` for the image tag | `tests/validations_test.yaml` |
| 2026-09-14 | **Validated on a kind cluster** (Kubernetes 1.34, arm64 images): install, migrations, upgrade, isolation. What used to be assumed is now measured: the read-only root filesystem holds for api, worker, sidecar, sandbox and the migrations Job; the superuser role does create the extensions; the NetworkPolicies keep the shell off the network, send the browser out through the proxy alone, and keep the api away from the sandbox; a `helm upgrade` rewrites no generated secret | `examples/local-kind/` |
| 2026-09-14 | MinIO images come from **quay.io**, not Docker Hub, which does not serve the `RELEASE.*` tags. Found by the cluster trial | `values.yaml` (`s3.image`, `s3.mcImage`) |
| 2026-09-16 | **MIT license** for this repository, at the root and inside the chart, stated on the OCI package (`org.opencontainers.image.licenses`). Distinct from the product's own license: the chart is deployment tooling, and the Enterprise modules it switches on stay governed by the Enterprise license and a signed key | `LICENSE`, `charts/rikoo/LICENSE`, `Chart.yaml` |
